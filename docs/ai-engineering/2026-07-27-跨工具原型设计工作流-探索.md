# AI 工程化探索 · 跨工具原型设计工作流

> **状态：探索阶段**（尚未固化为团队规范或自动 Skill）  
> **日期：2026-07-27**  
> **验证场：** 可视化刻意练习系统 · 学习计划「对话共创」模块  
> **目的：** 在实现学习系统的同时，沉淀「AI + 软件工程」中可复用的协作流程

---

## 1. 为何需要这条链路

旧习惯：

```text
澄清需求  =>  设计原型
```

问题：同一执行者同时做「定问题 / 定交互隐喻 / 填内容骨架」，最后一步容易塌回默认解（例如「一键生成 + 确认」），产品判断淹没在像素里。

本次认可并验证的探索链路：

```text
Cursor 澄清需求
  => Cursor 写原型设计提示词（设计简报）
    => Trae Work 设计高保真原型
      => 对照简报验收与归因
        => 用户视角愿用性判断（愿不愿真用）
```

核心增益不在「多用了一个工具」，而在多了一层**可版本化、可评审的中间表示（提示词 / 设计简报）**，把产品判断从最终界面里拆出来。  
验收也不止「提示词有没有兑现」——还要站在用户角度问：**看着这个原型，我愿意用这个产品吗？**

---

## 2. 角色与分工

| 阶段 | 谁做 | 产出 |
|------|------|------|
| 需求澄清 | 人 + Cursor | 问题定义、约束、反模式、范围裁切 |
| 写设计提示词 | Cursor（人审阅） | 给执行端的可复制简报（含路径、验收、不要做什么） |
| 出原型 | Trae Work 等专用执行端 | 高保真 HTML / 可感知交互 |
| 简报验收与归因 | 人（可辅以 Cursor） | 是否兑现简报；优因 / 缺口 |
| 愿用性判断 | 人为主；可让 Cursor 先扮用户再由人拍板 | 愿试用 / 愿长期用 / 卡住点；是否进入下一轮改简报或改原型 |

学习系统本身是验证场；流程文档才是 AI 工程化要沉淀的资产。

## 3. 步骤说明

### 3.1 需求澄清（Cursor + superpowers:brainstorming）

**使用的 SKILL：** [superpowers · brainstorming](https://github.com/obra/superpowers)（Cursor 插件 skills 中的 `brainstorming`）

**优点**

- 强制先探上下文、再澄清、再方案对比，适合把模糊动机压成可设计的需求。
- 「一次一问」、方案权衡、设计门禁，有利于深度分析，减少未审查假设直接开工。

**缺点**

- 容易**过度讨论**：问题拆太细、关卡式追问过多，打断收敛节奏。
- 本轮实践中已出现：用户明确反馈「问得太多」，需靠人打断或改用外部材料（如既有 SKILL 路径）加速收敛。

**探索期用法建议**

- 保留 brainstorming 的深度分析能力，但人要主动控场：一次只钉关键分叉，材料足够时直接给约束，不必走完技能清单上的每一问。
- 澄清产出仍写入 `docs/requirements/`（或等价需求文档），作为下游提示词的锚点。

### 3.2 写原型设计提示词（Cursor）

把已澄清需求**编译**成给 Trae Work（或同类工具）的提示词，建议至少包含：

1. **背景矛盾 / 反模式**（例如：禁止「一点就生成满意计划」）
2. **产品锚点**（主题、需求文档路径、现有高保真基线与设计体系）
3. **内容骨架来源**（优先给原始 SKILL / 规范的**文件路径**，少在提示词里复述全文）
4. **流程软约束**（主轴是什么、什么可选、不要做成强制关卡）
5. **交互硬约束与验收清单**
6. **明确不要**（范围外、视觉重做、真接 LLM 等）

本轮实例：`docs/prompts/2026-07-27-学习计划对话共创-TraeWork高保真提示词.md`

### 3.3 Trae Work 出高保真原型

- 执行端按简报生成可打开原型（本轮：`prototype/pages/learning-plan-cocreate.html`）。
- 要求高保真而非线框，并复用既有 design token / 页面基线，避免另起视觉语言。

### 3.4 简报验收与归因

对照提示词检查：交互隐喻是否兑现、SKILL 字段是否可核对、反模式是否被避开。  
同时做归因：哪些来自流程分层，哪些来自简报质量 / SKILL / 设计基线——避免把成功只归因于「换了工具」。

这一步必要，但**不够**：容易停在「实现了对不对」，而不是「值不值得用」。本轮起初也是习惯性让 Cursor「检查一下」，后来才意识到验收本身是流程里的一等公民。

### 3.5 用户视角愿用性判断（探索期正式纳入）

在简报验收之后，强制多问一句（人自问，或让 Cursor 先站在用户角度作答，再由人确认）：

> 看着现在的原型，我愿意用这个产品吗？

建议拆成两档，避免「好看 = 能用」：

| 档位 | 问题 | 用途 |
|------|------|------|
| 愿试用 | 会不会拿真实主题开一次严肃计划 / 走一遍主路径？ | 判断交互隐喻与内容骨架是否站住 |
| 愿长期用 | 会不会把它当成日常工具持续依赖？ | 判断是否接上执行闭环、信任细节、范围是否完整 |

回答应为带理由的判断，而不是分数：愿意的部分、卡住的部分、因此下一步改简报还是改原型 / 补链路。

**本轮实例（学习计划对话共创原型，2026-07-27）**

- **愿试用：是。** 左对话 / 右活文档、阶梯 + 核心 20% + 分节课表、局部修订痕迹，比「一键生成」更像能定制的计划工具；愿意拿真实主题开一轮并锁定。
- **愿长期用：否（尚早）。** 剧本约束与课表时长不一致（如每天 30 分钟 vs 10×2 小时）会伤信任；模块仍偏停在 P，未接工作台每日执行与防漂移；模拟对话未真正改文档——仍可能变成新的计划消耗，而非执行器。
- **验收启示：** 简报兑现 ≠ 愿用；愿用性判断应写回流程，避免只做符合性检查。

## 4. 本轮验证中的关键观察

- **流程分层有效**：提示词层把「共创 vs 一键生成」写死后，执行端更难退回旧默认。
- **路径引用优于长摘要**：三个 AI 学习 `SKILL.md` 用绝对路径交给 Trae 自读，比在提示词里手抄字段更干净、更不易失真。
- **软约束重要**：资料能力要保留，但不应做成「阶梯 → 资料 → 计划」强制三关。
- **brainstorming 需配人控场**：深度是优点，过度追问是已知代价。
- **验收要升维**：对照简报检查容易习惯性发生；必须再加「愿不愿意真用」的用户视角判断，才能接到下一轮产品决策。

## 5. 探索阶段边界（显式未定）

以下尚未固化，仅作后续迭代议题：

- 是否把本流程写成 Cursor Skill / Rule 自动触发
- brainstorming 的「停止追问」启发式如何写成可执行规则
- 提示词模板是否抽成固定章节骨架
- 简报验收 + 愿用性判断是否标准化为检查表（含「愿试用 / 愿长期用」两档记录）  
  → **部分进展（2026-08-12）：** 打磨期愿用已收成 [三层评测](./2026-08-12-三层评测方法.md) + [Persona/冒烟方法](./2026-08-12-Persona与冒烟回归方法.md)；原型期两档检查表仍可另做
- 其他制品（详细设计、实现计划、代码）是否复用同一「中间表示」模式
