## 1. 与 07-27 工作流的关系

07-27 文档回答的是：**用什么链路出原型**（Cursor 简报 → Trae 出图 → 验收 → 愿用）。

本文回答的是：**人与 AI 在多轮里各自固定干什么**——尤其是需求如何在过程中被共创、再沉淀。

```text
07-27：制品流水线（简报 / 原型 / 验收）
07-29：协作行为模式（分工 / 回合 / 需求共创）
08-12：打磨期三层评测（代码 / 功能 / 产品）← 愿用层的日常化
```

二者叠加才完整：没有行为模式，流水线会变成「AI 瞎猜隐喻 + 人对着像素改」；没有流水线，行为模式落不到可版本化制品。打磨期愿用判断的可复用口径见 [三层评测方法](./2026-08-12-三层评测方法.md)。

## 2. 总环：外执行 · 内编译 · 人拍板

```text
人：体感缺口 / 验收请求 / 产品判断
  → AI：取证 → 结构化结论
    → 人：短决策 或 纠偏 或 外抛 Trae
      → AI：编译中间表示（prompt / spec）
        → 人/Trae：改像素
          → AI：再验收（简报层 → 愿用层）
            → 人：要求沉淀 → AI：回写 requirements（需求共创闭环）
```

| 角色 | 固定职责 | 不该抢 |
|------|----------|--------|
| **人** | 产品隐喻、范围裁切、外工具出图、愿用终裁、发起需求沉淀 | 不必写长简报 |
| **Cursor** | 取证、选项化、编译简报/规格、分层验收、代言用户初稿、**按人指令沉淀需求** | 不独自宣布「需求已定死」 |
| **Trae Work** | 高保真像素 | 不定需求 |

## 3. 新模式：需求共创（相对 07-27 的增量）

### 3.1 旧隐含假设

07-27 链路容易读成：

```text
需求先澄清清楚  =>  再写简报  =>  再出原型
```

实践里并非如此：**有用的需求往往在「简报 → 原型 → 验收 → 别扭/否决」之后才被说清。**

### 3.2 定义

**需求共创** = 需求不在开局一次定死；人与 AI 在原型/验收轮次中反复讨论（含人纠偏、否决、范围剥离），再由人触发、**AI 负责把定案与否决项写入 `docs/requirements/`**，供后续简报锚定。

| 谁 | 在需求共创里做什么 |
|----|-------------------|
| 人 | 提供体感与正确主轴；决定「可以进需求澄清了」；审阅回写是否失真 |
| AI | 整理讨论过程（含被否决路径）；写成专题/总纲增量；链回 prompts/specs |

### 3.3 实例（冷启动）

| 阶段 | 当时「需求」状态 | 发生了什么 |
|------|------------------|------------|
| IA 后 | 回访可走通即可 | 发现冷启动断链 |
| 冷启动 v1 | AI 编译成「信息→来源→导入占位→核心预览」 | 原型验收否决 |
| 人纠偏 | 正确主轴被说清 | 信息→阶梯共创→资料共创→三阶段计划 |
| 沉淀 | 人：「可以放到需求澄清里」 | AI 写专题需求 + 回写总纲 §9 |

产物：`docs/requirements/2026-07-29-主题创建与冷启动共创-需求澄清.md`（正文含「澄清过程」表，刻意保留否决路径）。

### 3.4 与「开局 brainstorming」的区别

| | 开局澄清 | 需求共创 |
|--|----------|----------|
| 时机 | 动手前 | 贯穿原型与验收轮次 |
| 输入 | 动机、约束、选择题 | 体感、否决、正确主轴、愿用卡住点 |
| 风险 | 问太多、空转 | 若不沉淀，定案只活在聊天/简报里 |
| 产出 | 初版 requirements | **修订后的** requirements（专题 + 总纲回写） |

二者都要；需求共创是对「需求一次性定死」幻想的修正。

### 3.5 成功标准（探索期）

1. 重要定案能在 `requirements/` 找到，而不只在某次 prompt 里。  
2. **否决项**一并写明，降低回流（如「勿再做导入占位」）。  
3. 回写由人触发或明确确认，避免 AI 擅自改需求口径。

## 4. 其余可复用子模式（两轮会话重复出现）

| # | 模式名 | 人 | AI | 例子 |
|---|--------|----|----|------|
| 1 | **缺口开场** | 迷路 / 别扭 / 不行 | 取证后下判 | 「没交互」「说不上来的别扭」 |
| 2 | **选项微协议** | 回 `B` / `方案1` / `ok` | 2–3 档方案后再展开 | 冷启动 A/B/C；IA 选 C |
| 3 | **中间表示编译** | 「写一版提示词」 | Trae 可复制简报 | 接线 / IA / 冷启动 v2 |
| 4 | **外执行内验收** | Trae 画完回来说验收 | 对照简报；区分工具质检 vs 产品 | 「画好了，验收」 |
| 5 | **验收分层** | 指定验哪一层 | 接线→结构→语义→愿用 | 接线过仍别扭 → 开 IA |
| 6 | **双档愿用** | 「愿意用吗？」 | 愿试用 / 愿长期用 + 卡住点 | 扮用户走冷启动 |
| 7 | **人纠偏重编译** | 给出正确主轴 | 承认错、作废旧路径、重写 | v1→v2 |
| 8 | **范围剥离** | 「这点不用了」 | 下一轮简报去掉该项 | 布局交 Trae 自修 |
| 9 | **需求共创** | 「沉淀进需求澄清」 | 写专题 + 回写总纲 | 见 §3 |

1–8 支撑把原型做出来；**9 把讨论变成可继承的产品真相。**

## 5. 回合剧本（诊 · 决 · 编 · 验 · 沉）

相对 07-27 的四步流水线，协作回合多一拍 **沉**：

1. **诊**：缺口 → 取证下判  
2. **决**：选项化 → 人短指令或纠偏  
3. **编**：prompt / spec  
4. **验**：外端出图 → 简报验收 → 愿用  
5. **沉**：人触发 → 需求共创回写（定案 + 否决 + 仍开放）

缺「决」→ AI 空转追问；缺「编」→ 对着像素扯；缺愿用「验」→ 假通过；缺「沉」→ 下一轮从聊天记录考古。

---

## 6. 明确不是固定模式的

- AI 一次猜对产品隐喻  
- 开局把需求问到「完美」再动手  
- Trae HTML 质检 passed = 产品验收通过  
- 「做实一点」= 加表单关卡  
- AI 未经人确认就改 requirements 口径  

---

## 7. 对 AI 工程化的含义

可沉淀的优先级（探索建议）：

1. **需求共创回写协议**（人触发、含否决、链总纲）  
2. 选项微协议 + 简报章节骨架  
3. 验收分层 + 愿用双档检查表  

不要优先自动化「替人决定正确流程」。
