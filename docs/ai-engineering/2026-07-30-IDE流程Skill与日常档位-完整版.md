## 1. 背景：为什么要单独谈 IDE 流程 Skill

开发阶段容易产生一个疑问：**AI Native IDE 还需要人为安装 Skill 吗？**

两段真实对照：

- **高流程**（装 Superpowers）：进入开发前的决策更完整，但单位时间产出被「问答税」吃掉——体验是不断在回答问题。  
- **低流程**（关掉后直做）：在原型与 docs 已齐时，初版「过得去」且更快。

结论先写在前面：

> **开发阶段不必为了「显得 AI Native」而装一堆流程型 Skill。**  
> IDE 流程 Skill 不是能力插件，是把某种工程纪律外置给 Agent 执行的「运行时策略」。值不值得开，取决于这一轮要买的是速度还是抗熵。

## 2. 完整论述：IDE 流程 Skill 与日常工作模式

> 以下为探索对话中「第二次深入回答」的全文整理，略作标题编号以便检索；论述内容保持完整。

### 2.1 它在 AI 工程化里到底是什么

你的判断可以落成一句工作原则：

**IDE 流程 Skill 不是能力插件，是把某种工程纪律外置给 Agent 执行的「运行时策略」。** 值不值得开，取决于你这一轮要买的是「速度」还是「抗熵」。

AI 工程化大致在叠三层：

| 层 | 载体 | 作用 |
|----|------|------|
| 知识 | docs / 原型 / 代码本身 | 告诉 Agent「世界长什么样」 |
| 约束 | Rules / AGENTS.md | 告诉 Agent「别踩哪些坑」 |
| 流程 | IDE 流程 Skill | 告诉 Agent「先干什么、再干什么、什么时候必须停下来问你」 |

Superpowers 属于第三层，而且设计得很极端：`using-superpowers` 写的是「哪怕只有 1% 可能相关也必须先调 Skill」；`brainstorming` 写的是「任何创意工作都必须先过这套，简单项目也不能例外」。

所以你会感到「不断在回答问题」，不是模型笨，是流程在**强制把你拉回决策位**。它默认：人的判断比模型的一次拍板更可靠，宁可多问，也不让你在错误假设上高速施工。

这对「从零摸需求」有价值；对「原型已定、文档已写、就差实现」是负资产——直做初版那一段对话就是证明。

### 2.2 两段对话测出的曲线

- **高流程**：进入开发前的决策质量更高，但单位时间产出被问答税吃掉。  
- **低流程**：在上下文已够时，初版「过得去」且快。

这说明对探索型工作，**瓶颈通常不在「Agent 会不会写」，而在「这一轮不确定性有多高」**。

可以画成：

```text
不确定性高  → 流程 Skill 划算（防返工 > 问答税）
不确定性低  → 流程 Skill 亏本（问答税 > 防返工）
```

日常模式不该是「永远开」或「永远关」，而该是：**按不确定性开关档位。**

### 2.3 为什么「整包 Superpowers」很难成为默认模式

它把工程方法论做成了**全局拦截器**：

1. **触发过宽**：功能、组件、行为改动都算「创意工作」→ 几乎每条开发对话都进 brainstorming。  
2. **终端态固定**：brainstorming 结束后只许进 writing-plans，不让直接写——适合大项目，不适合「补一页 UI」。  
3. **把人当稀缺资源**：每一步都要 approval；若本就清楚要什么，就变成复读机。  
4. **与「上下文已进仓」冲突**：已有需求澄清、交付说明、HTML 原型——再走一遍澄清，是在重复支付已经付过的认知成本。

对团队新人、外包、或需求模糊的产品周，它是护栏；对**「产品负责人 + 唯一用户 + 文档齐全」的探索者**，默认开等于给自己加了个项目经理，而往往并不缺这个角色。

### 2.4 更适合的日常模式：三档运行时

把 IDE 流程当成**可切换的工程模式**，而不是装一次就永久生效的信仰：

| 档位 | 何时用 | Agent 行为 | 你付出的 |
|------|--------|------------|----------|
| **L0 直做** | bugfix、按原型还原、已知契约改 API/UI | 读上下文 → 改 → 自验 | 几乎不问 |
| **L1 短计划** | 半天以上、跨前后端、有 2–3 个技术分叉 | 先给一页方案，你点头再写 | 一次决策 |
| **L2 重流程** | 新子系统、协议重设计、安全/数据模型大改、多 Agent 并行 | brainstorm → spec → plan → 分任务执行 → 验证 | 多轮问答，换少返工 |

对应落地（不必再背整包）：

- **默认 L0**：关掉 Superpowers 自动触发，或整包禁用。  
- **升到 L1**：一句话点名即可——「先给方案，我确认后再写」。这比装 brainstorming 轻一个数量级。  
- **升到 L2**：才值得手动 `/brainstorming` 或打开流程包；且最好限定在「新开对话、任务边界清晰」时用。

L1 才是多数「认真一点的日常开发」的甜点区——**一次对齐，然后放权**，既保留工程感，又不把对话变成问卷。

### 2.5 流程 Skill 真正该沉淀的，不是问卷，是「失败模式」

若把这当成长期 AI 工程化探索，建议反过来建 Skill：**只编码反复踩过的坑**，而不是编码通用软件工程教科书。

**好的个人流程 Skill：**

- **触发窄**：`Use when 共创协议变更 / 领域模型迁移 / 准备对外演示前`  
- **步骤短**：3–7 步，可跳过  
- **允许直通**：若用户说「按现有 docs 直接做」，必须退出流程  
- **产出物明确**：一份短决策记录或 checklist，而不是无限澄清  

**差的个人流程 Skill（Superpowers 偏这侧）：**

- 触发宽到「任何创意工作」  
- MUST 满天飞  
- 把「问人」当成默认进度条  
- 不允许声明「上下文已足够」  

操作口令可以写成一句：

> **默认直做；只有当预感返工会贵过问答时，才升档。升档用短计划，不默认用整包方法论。**

### 2.6 这会不会成为日常工作模式？

会，而且很可能比「装不装 Superpowers」更本质。

真正在探索的是 **人机分工的控制面**：

- 模型负责生成与搜索  
- 仓库负责长期记忆  
- Rules 负责硬约束  
- **流程 Skill 负责「何时必须把方向盘还给你」**  

成熟形态大概是：

1. **仓库即流程底座**（docs + 原型 + 契约）→ 压低 L2 需求频率  
2. **薄 Rules**（技术栈、语言、禁止事项）→ 稳定 L0 质量  
3. **少量自建窄 Skill**（调试、发布前验证、某类重构）→ 按需升档  
4. **重型流程包作工具箱，不作默认 OS** → 避免问答税常态化  

两段真实对话完成了 A/B：高流程提高决策完整度，低流程提高交付速度；对「探索型个人工程」而言，**默认低流程 + 按不确定性升档**，才是可持续的日常模式。

一句话收束：

> **IDE 流程 Skill 值得成为工具，不值得成为默认人格。**  
> 日常开 L0/L1，只在返工成本明显升高时切 L2——这比争论「还要不要装 Skill」更接近 AI 工程化本身。

## 3. 「设计 L2、初版 L1」算不算最佳实践？

**大体对，但别当成固定配方。**

更准的说法是：

| 阶段 | 默认档 | 为什么 |
|------|--------|--------|
| **产品设计 / 定方向** | **L2** | 不确定性最高，问答税换的是少做一整个错产品 |
| **初版开发（边界已清）** | **L1** | 一次对齐技术切法与范围，然后放权写；不必再走完整 brainstorm |
| **定稿后的补页面 / 修 bug / 小迭代** | **L0** | 上下文已在仓库里，再问就是重复劳动 |

所以「设计 L2、初版 L1」是**常见甜点路径**，尤其适合「先定原型再开工」的节奏；但它不是最佳实践本身，**按不确定性升档**才是。

两个例外：

- 设计阶段若已经自己写清需求/原型，L2 可以压成「短确认」甚至跳过——已付过认知成本。  
- 初版若仍在拍关键技术分叉（存哪、AI 边界、V1 切到哪），L1 不够时就升半档：多一次决策，不必整包 Superpowers。

收束：

> **设计偏 L2、初版偏 L1、之后偏 L0——对，当作默认；遇低不确定就降，遇高返工风险就升。**

## 4. 大厂公开实践与总结出的最佳实践

公开材料里，这几家**几乎没人把「整包方法论 Skill」当默认 OS**；共性是：**仓库当记忆、Skill 当窄能力、流程按任务升档**。这与上文 L0/L1/L2 高度同向。

### 4.1 对照一览

| 公司/产品 | 公开重心 | Skill 怎么用 | 更像哪一档 |
|-----------|----------|--------------|------------|
| **Anthropic / Claude Code** | 内部上百个 Skill，分 9 类；验证类投入回报最高 | 窄、单职责；按需加载；gotchas；可用 `disable-model-invocation` 控手动 | 默认 **L0**，验证/发布升档 |
| **OpenAI / Codex** | Harness engineering：人造环境，Agent 写代码 | 短 `AGENTS.md` 当地图 + `docs/` 当真源；Skill = 可重复工作流 + MCP | **L1 计划进仓**，日常执行偏 L0 |
| **阿里 / Qoder（原灵码）** | 多智能体 + Quest 规划 + 企业 Skill 资产 | Skill/Subagent/Command 产品化；复杂任务走规划窗 | 产品内建 **L1**（Quest），企业沉淀 Skill |
| **Trae** | 对齐 Agent Skills 标准；SOP 封装 | 场景化、按需加载；项目/全局分层；社区市场 | 偏 **L0 能力包**，非强制问答流 |

### 4.2 Anthropic / Claude Code：Skill 是专业手册，不是每次都 brainstorm

他们自己总结：内部 Skill 落在 9 类——库/API 参考、**产品验证**、数据拉取、团队自动化、脚手架、代码质量、CI/CD、Runbook、基础设施。明确建议：

- **一个 Skill 只干一类事**  
- 别写模型本来就会的废话  
- 最高价值是 **Gotchas** 和 **Verification**（有人甚至值得花一周把验证 Skill 做极致）  
- 用文件系统做 **progressive disclosure**（SKILL.md 指向 references/scripts，按需再读）

关键信号：他们推的是「失败模式编码 + 可执行检查」，不是「所有创意工作先问人」。这和 Superpowers 那种全局拦截差得很远。

参考：[Lessons from building Claude Code: How we use skills](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills)

### 4.3 OpenAI / Codex：人做 harness，Agent 做执行；流程进仓库

Harness 团队公开实验：数月内约百万行、上千 PR，原则是 **Humans steer, Agents execute**。他们试过「一个超大 `AGENTS.md`」——失败了（挤占上下文、规则腐烂、无法机械校验）。改成：

- `AGENTS.md` ≈ 100 行**目录**  
- `docs/`（设计、规格、exec-plans、质量分）才是系统真源  
- Skill + 本地可观测性/浏览器，让 Agent **自己验**  
- 复杂工作用 **execution plans 进 git**，不是无限澄清对话  

这几乎就是：

```text
设计/大改 → 写进 docs（L2 产物化）
     → 执行前短计划（L1）
     → 日常改代码靠仓库可读性（L0）
```

参考：[Harness engineering](https://openai.com/index/harness-engineering/)

### 4.4 阿里 / Qoder（通义灵码）：把 L1 做进产品，Skill 做企业资产

公开叙事更偏「多智能体软件工厂」：规划 / 搜索 / 生成 / 单测 / 调试；Quest 做任务拆解与跟踪；Skill、Subagent、Command 可自定义；企业侧强调 Skill 云端管理、数字员工、隔离沙箱长任务。

特点是：**流程能力产品化**（Quest ≈ 内建短计划），而不是让用户装第三方「必须先 brainstorm」插件。Skill 定位接近 Anthropic——可复用场景能力，尤其适合组织内 SOP。

### 4.5 Trae：标准对齐 + SOP，强制流程包反而还没完全吃下

官方文档把 Skill 写成「专业能力说明书」：测试流、评审、业务约束、技术栈约定；按描述按需加载，避免塞爆上下文。社区还有人提：Superpowers 那套 SKILL 生态尚未完全兼容——侧面说明 Trae 主路径是标准 Agent Skills，不是重型流程宗教。

### 4.6 总结：可抄的「大厂最佳实践」（个人工程版）

顶级厂商公开实践的公约数：

1. **不默认 L2 问答**——高不确定时把决策写成 `docs/` / spec / plan，而不是每轮聊天复读。  
2. **日常靠 L0**——仓库可读、Rules/AGENTS 薄、Skill 窄且按需。  
3. **重复工作升到「可调用 Skill」**——验证、发布、脚手架、oncall（对应 Anthropic 的 verification / CI / runbook）。  
4. **复杂任务用 L1 产物**——OpenAI 的 exec-plans、阿里的 Quest：一次对齐，然后放权。  

个人探索可抄的不是「装哪个大厂同款插件」，而是：

| 向谁学 | 抄什么 |
|--------|--------|
| OpenAI | 把规格/计划/约束**版本化进仓**；`AGENTS.md` 当地图，不当事典 |
| Anthropic | 只为**反复踩坑与验证**写窄 Skill；一类一事；渐进披露 |
| 阿里 | 复杂任务显式走规划窗（Quest/L1），日常别绑死 |
| Trae | Skill 当 SOP，不当事事审批机 |

**大厂版相对个人甜点路径的升级一句：**

> **L2 的产出应进仓库，而不是留在对话里；L1 是短计划或 Quest；Skill 主要服务 L0 的正确率与可重复性，而不是劫持每次对话。**

### 4.7 需要诚实的一点

以上是**公开博文/文档/产品能力**，不是内部真实排班表。各家不会把「工程师一天开几次 brainstorm」写成 KPI。能确认的是方法论方向：

> **环境与反馈回路 > 厚流程插件。**

**立即执行：**

4. 试用一周后按操作卡末尾三问决定是否固化成 Rule  

**不在本文范围：**

- 产品能力 Skill 的安装与编排（属应用架构，不属 IDE 流程档位）  
- 是否把本文整篇塞进 Agent 上下文（不建议；日常只引用操作卡即可）
