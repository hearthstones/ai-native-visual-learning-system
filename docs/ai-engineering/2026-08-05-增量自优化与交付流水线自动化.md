## 2. 实践观察（触发本文）

近期使用 Cursor 的三点观察：

1. **产品设计前期需要大量澄清**；进入开发后的**增量需求**，跳过原型直接开发，效果也足够好。  
2. **MVP 之后**，直接让 AI 走一遍全流程并优化体验，往往比人机一步步协作打磨更连贯。  
3. **Code review 与 AI 验收**每次都能找出新问题，但很消耗 token。

这三点不是互相独立的技巧，而是同一条曲线上的不同位置：**不确定性下降后，该切换工作模式，并把可重复环节外置为自动化。**

## 3. 核心判断

### 3.1 一句话

> **自动化的是「从已批准目标到可验证交付」的路径，不是「自动决定做什么产品」。**

### 3.2 两类可自动化对象

| 类型 | 例子 | 性质 |
|------|------|------|
| **质量闭环** | code review、全流程自检、回归巡检 | 可重复、有判据、可回放 → **适合常驻自动化** |
| **增量交付编排** | 多 AI-PM 辩论 → 定稿 → 写代码 → 对照验收 | 在骨架已定、约束可检索时 → **可高度自动化** |

### 3.3 人仍必须在环的位置

| 能自动化 | 仍需人（或等价外部真相） |
|----------|---------------------------|
| 在既有愿景/约束内生成方案并互驳 | 目标优先级、做/不做 |
| 把需求压成范围与验收标准 | 用户真实反馈、风险偏好 |
| 按定稿实现并跑通主路径 | 定稿本身是否值得做 |
| 发现实现与定稿不一致并回修 | 接受技术债、延期、降级 |

多 AI-PM 有意义的前提是：他们争论的是**如何满足合同（定稿）**，而不是重新发明产品方向。

## 4. 阶段模型：何时人主导，何时放权流水线

### 4.1 三阶段

| 阶段 | 典型信号 | 默认模式 | 人的职责 | AI 的职责 |
|------|----------|----------|----------|-----------|
| **探索期** | 新产品/新子系统；隐喻未定；信息架构未稳 | 人主导澄清；可出原型；对应 07-30 的 **L2** | 目标、边界、隐喻、终裁 | 提问、选项化、编译需求/简报 |
| **增长/打磨期** | MVP 已可用；主路径与数据模型已定；增量多为一致性与体验 | **自动化为主**：多角色定稿 → 直开 → 全流程自检；对应 **L0/L1** | 批准目标与优先级闸门；抽检 | 辩论定稿、实现、端到端优化、回炉 |
| **常驻质量** | 任意合并前后 | **完全自动化**门禁 | 只处理升级项与策略例外 | review / 回归 / 体验巡检 |

### 4.2 阶段切换清单（操作口径）

**仍停留在探索期（不要全自动）若：**

- [ ] 还说不清「用户完成的主任务是什么」
- [ ] 信息架构或核心对象模型可能被推翻
- [ ] 需要新的产品隐喻或全新页面范式
- [ ] 验收标准无法写成可检查项（只能靠「感觉好不好」）

**可切换到增长/打磨期（放权流水线）若：**

- [ ] 主路径已可走通（冷启动 → 主题 → 计划/练习/复习等）
- [ ] 增量需求能用现有组件与路由表达，不必先画新原型
- [ ] 约束可从 `docs/`、代码与既有 IA 检索到
- [ ] 能写出本文 §5 的定稿合同最小字段

**应打开常驻质量自动化若：**

- [ ] 已有可合并的主分支与可复现的关键路径
- [ ] review / 自检结果能结构化为 finding（可修或明确 wontfix）
- [ ] 愿意为「拦合并」支付固定 token，而不是每次全仓哲学复扫

### 4.3 与「跳过原型 / 全流程自走」的对齐

| 做法 | 适用阶段 | 注意 |
|------|----------|------|
| 跳过原型，增量直开 | 增长/打磨期 | 沿用已落地的交互范式；大改 IA 仍要回探索期 |
| MVP 后 AI 全流程自走优化 | 增长/打磨期 | 优于人机逐步抠局部；但需 **stop condition**，避免无限 polish |
| 每次深度 review + 全量验收 | 成本高 | 改为：大改深度扫；日常只扫 diff + 遗留项；反复问题沉入 Rule/清单 |

## 5. 定稿合同：机器可执行的硬接口

「定稿」必须是合同，不是聊天纪要。最小字段集：

```text
1. Goal          要改善的用户结果（一句话）
2. In scope      做什么
3. Out of scope  明确不做什么
4. Constraints   必须沿用的 IA / 数据边界 / 视觉语言 / 非功能约束
5. Acceptance    可脚本化或可 Agent 走查的检查项
6. Stop          改到什么程度停（防无限优化）
```

没有这六项，流水线缺少停止条件与验收锚点，多 PM 辩论只会产出「自洽但不可判定」的方案。

## 6. 目标流水线（增长/打磨期）

```text
需求输入（人或简报）
  → 1～3 个 AI-PM（不同视角）辩论
  → 产出定稿合同（§5）
  → 人：批准目标 / 优先级（闸门；可抽检合同）
  → AI 实现（默认跳过原型，L0/L1）
  → AI 全流程自检（对照 Acceptance）
  → 不通过 → 回炉实现或回炉辩论
  → Code review / 安全等门禁
  → 合并 或 记债（结构化 wontfix）
```

### 6.1 建议的 AI-PM 角色分工（1～3 个）

不必每次三人齐上；按变更风险选：

| 角色 | 盯什么 | 典型否决 |
|------|--------|----------|
| **一致性 / IA** | 是否破坏既有导航、对象模型、用语 | 「又发明一种卡片范式」 |
| **体验 / 主路径** | 空态、反馈、断链、文案是否帮用户完成任务 | 「功能对了但走不通」 |
| **风险 / 范围** | 是否越界、是否该降级、token/工期是否失控 | 「这是新子系统，应回探索期」 |

### 6.2 Review / 自检自动化原则

审查与自检适合做成常驻自动化，但必须满足：

1. **判据显式**：过 / 债 / 拦合并，三分清楚  
2. **范围收敛**：按 diff 与风险面扫，禁止无重点全仓复扫作为默认  
3. **结果结构化**：finding → 可执行修复，或明确 `wontfix` + 理由  
4. **频率分层**：大改动深度一轮；日常增量只盯变更面 + 上次遗留

Token 贵的往往不是「AI 会找问题」，而是**缺少判据与范围的重复全量辩论**。

---

## 7. 对「需求到开发能否全自动」的直接回答

**在骨架已定的阶段：可以。**

更精确的表述：

- **可以自动化：** 需求提出 → 多角色辩论 → 定稿 → 开发 → 对照验收 → review 门禁  
- **前提：** 人批准的目标 + 机器可读定稿（§5）+ 可自动验收  
- **不能省略：** 目标所有者（人）对「做什么 / 值不值得做」的闸门  

自动化交付流水线 ≠ 自动化产品方向。
