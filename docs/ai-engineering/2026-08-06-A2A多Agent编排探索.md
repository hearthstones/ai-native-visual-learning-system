## 1. 一句话

**MCP = Agent 的手（连工具/数据）**  
**A2A = Agent 的同事（连其他 Agent）**

本项目已验证有效的是：**流程分层 + 制品交接 + 人在闸门**；不等于必须上跨厂商 A2A 协议。

---

## 2. 设想中的软件工程链路

会话中的抛砖：

```text
工作流 Agent（Hermes）
  → 需求（Codex）
  → 原型提示词（Codex）
  → 原型设计（Trae Work）
  → 需求&原型评审（Hermes / WorkBuddy）
  → 代码开发（Claude Code / Cursor）
  → 代码审查（Hermes）
  → 功能验收 → 用户体验
```

画成 A2A 形态时，编排 Agent **不亲自**写 PRD / 画原型 / 写代码，只做：发现 Agent（Agent Card）→ 下 Task → 收 Artifact → 决定下一步或升级给人。

| 概念 | 作用 | 类比 |
|------|------|------|
| Agent Card | 我能干什么、怎么连 | 岗位说明书 |
| Task | 有生命周期的工单 | Issue |
| Artifact | 任务产出 | PRD / 原型 / PR / 报告 |

## 3. 与本仓库已有实践的映射

| A2A 设想环节 | 本项目实际做法（无需 A2A） |
|--------------|---------------------------|
| 需求 | Cursor 澄清 → `docs/requirements/` 回写（07-29） |
| 原型提示词 | `docs/prompts/` 简报（07-27） |
| 原型 | Trae Work；人控场 |
| 评审 / 愿用 | 简报验收 + 愿用判断；后人机分层验收 |
| 开发 | Cursor L0/L1/L2（07-30）；增量期可跳过原型（08-05） |
| 代码审查 | `/code-review`、缺陷优先 |
| 功能 / 体验 | 冒烟脚本 + Persona（见三层评测文档） |

**有价值的是「环节与闸门」；换品牌 Agent 用协议焊死，不是同一回事。**

## 4. 生态事实（会话调研摘要，会过时）

调研时点约 2026-08-06，结论倾向：

| Agent | 原生 A2A | 备注 |
|------|:--------:|------|
| Hermes | 较强 | 适合做编排层候选 |
| WorkBuddy | 部分 / 编排向 | 勿默认完整 Server |
| Codex / Trae / Claude Code / Cursor | 基本否 | MCP（或 ACP）优先；靠社区 bridge |

**Bridge：** 多为社区开源旁路进程（包装 CLI），不是 IDE 厂商一等公民；运维与权限成本自己扛。示例方向（名称会变）：`coding-agent-a2a`、`cursor-agent-a2a`、`a2claude`、`a2a-bridge` 等。

落盘时若要再上协议，应重新调研，勿把上表当永久真源。

## 5. 关键判断：必要还是炫技

**对当时本项目（一人主导、学习系统验证场）：整条跨厂商 A2A 流水线，炫技成分大于刚需。**

| 环节 | 必要？ |
|------|:------:|
| 探索 / 增长 / 常驻质量分层 | ✅ |
| 定稿 → 实现 → 自检 / CR | ✅ |
| 每阶段换一个品牌 Agent | 弱 |
| 用 A2A 正式互连 | 多数时候否 |

A2A 值得认真上的信号（至少两条）：组织边界、运行边界（跨机/账号）、强供应商可替换审计、每天大量同类工单。

个人/小团队更贴文档的够用形态：

```text
探索期（L2）：人 + 一个强 Agent
增长期（L0/L1）：同一 IDE 内定稿 → 实现 → 自检/CR
常驻质量：CI + review；体验用 Persona/冒烟，不必跨产品协议
```

「多 AI-PM」用**同工具多角色提示 / 多会话**即可（08-05），不必 Codex→Trae→Cursor 经 A2A 交接。
