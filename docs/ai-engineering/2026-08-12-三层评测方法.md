## 1. 核心三分法

| 层 | 手段 | 核心问题 | 典型失败形态 |
|----|------|----------|--------------|
| **代码** | Code review（缺陷优先） | 有没有 Bug | 逻辑错、边界漏、契约不一致 |
| **功能** | AI 功能验收 / 主路径冒烟 | 能不能用 | 偶发胡答、格式漂移、关键路径挂 |
| **产品** | AI 用户体验 / Persona 走查 | 愿不愿用 | 能跑但不顺、不信、不值 |

打磨阶段最常见的错位：

- 把第 3 层的「别扭」当成第 2 层去改 prompt  
- 把第 2 层的「偶发不可用」当成第 1 层去堆防御性代码  

**先定层，再选动作。**

## 3. 扩展：评测系统化时再补的维度

三层回答「问什么」。工程化时还可叠加（不必每次全开）：

### 3.1 发布前之外：数据层与线上层

| 层 | 核心问题 | 典型手段 |
|----|----------|----------|
| 数据 / 知识 | 喂给模型的东西对不对 | 语料抽检、引用可追溯、时效、覆盖盲区 |
| 线上 | 真实分布下还稳不稳 | 反馈聚类、错误桶、（有流量时）影子 / A/B |

本项目暂停前以单人自用为主，线上层弱；资料偏官方等问题已升格为能力/身份问题，见 [诚实记账的工程含义](./2026-08-12-能力诚实记账的工程含义.md)。

### 3.2 正交三轴（每一层内部）

- **正确性**：事实、逻辑、约束是否成立  
- **稳健性**：换说法、换边界、加噪声是否仍成立  
- **成本**：延迟、token、人工介入、失败恢复成本  

「能用」但慢/贵/要人盯 → 产品层仍可能「不愿用」。

### 3.3 评测对象：模型 ≠ 系统 ≠ 产品

| 对象 | 在比什么 |
|------|----------|
| 模型 | 同一题换模型 |
| 系统 | 检索 + 工具 + 编排 + 降级整条链路 |
| 产品 | 用户目标是否更快、更少挫败地完成 |

功能验收失败，经常是系统问题（状态机、契约、超时），不是模型「变笨了」。

### 3.4 证据强度（由高到低）

1. **硬判定**：schema、权限、禁止词、引用存在、HTTP 契约  
2. **对照集**：golden cases / 固定场景回归包  
3. **裁判模型 / Persona**：可扩展，必须校准，不能当唯一真相  

节奏：硬判定保底 → 对照集防回归 → Persona/裁判筛查 → 人审抽检。

## 4. 失败分类（修之前先入桶）

建议固定桶，复盘才能对上动作：

| 桶 | 多落在哪一层 | 典型修法 |
|----|--------------|----------|
| 幻觉 / 事实错 | 功能 / 数据 | 约束、检索、拒答策略 |
| 拒答过度或不足 | 功能 | prompt / 策略 |
| 格式 / 契约破坏 | 代码 / 功能 | 校验、测试、schema |
| 工具调用错误 | 系统 | 编排、超时、降级 |
| 体验摩擦（步数多、不确定、不可控） | 产品 | 文案、默认值、流程 |

## 5. 门禁对齐

| 层 | 门禁角色 | 强度建议 |
|----|----------|----------|
| Code review | 合并门禁 | 阻塞缺陷必须清；债与 wontfix 结构化记录 |
| 功能验收 | 发布 / 封板前门禁 | 核心场景包通过率；含失败与降级路径 |
| 体验评测 | 产品门禁 | 关键旅程完成率 / 二次修改率阈值；大改交互后必跑 |

没有门禁的评测，最后都会变成「看过了、感觉还行」。

与 08-05 定稿合同对齐：`Acceptance` 应尽量写成可脚本化或可 Agent 走查的检查项；停条件写在 `Stop`，防无限 polish。

## 6. 各层操作口径（本仓库）

### 6.1 代码层 · Code review

- **默认**：缺陷优先，按 diff / 风险面扫，禁止无重点全仓复扫当日常  
- **输出**：阻塞 / 非阻塞 / 债（wontfix + 理由）  
- **实践**：会话内 `/code-review` 或审查子代理；结论应能直接开修  

### 6.2 功能层 · 验收与冒烟

- **脚本**：`scripts/seed_three_themes_flow.py`（三主题主路径）  
- **口径**：mock 保 CI/本地快反馈；live 封板或大改 AI 路径时再跑  
- **通过**：主路径无阻断级崩溃；偶发 502 记入稳健性债，不假装「全绿」  

详见 [Persona 与冒烟回归方法](./2026-08-12-Persona与冒烟回归方法.md)。

### 6.3 产品层 · 体验

- **脚本试验**：`scripts/persona_ux_trial.py` + [08-07 记录](./2026-08-07-persona-ux-trial.md)  
- **方法约束**：同任务、强制模板、只收阻塞级建议、改完回归；防自嗨见下节  
- **真人**：关键路径偶发 2–3 人 × 15 分钟打脸 AI 结论（有条件时）

## 7. Persona 体验评测：有用但易自嗨

**定位：** 打磨期的结构问题预筛，不是体验真相的唯一来源。

**能提升体验的条件：**

1. 有真实任务脚本（不是「随便玩玩」）  
2. 产出能变成可验证改动（文案 / 流程 / 默认值）  
3. 改完回归同一任务  
4. 偶尔用人校准  

**自嗨征兆：** 三人设空聊、建议不可验证、「研究员说好了」=「用户愿用了」。

「初 / 中 / 高」建议定义为 **AI 使用成熟度**，不要与「学科专家 vs 小白」混用。本仓库 08-07 试验用的是场景人格（通识 / 工程师 / 忙碌产品），与成熟度分级是两套可用切法——选一种跑一轮即可，不要同时养两套常驻团队。

---

## 8. 口令

**对不对 · 能不能用 · 愿不愿用——先定层再动手。**  
**硬判定保底，对照集防回归，Persona 只做预筛。**  
**没有门禁的评测等于没评。**
