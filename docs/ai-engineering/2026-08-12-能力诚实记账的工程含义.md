## 2. 核心工程教训

### 2.1 叙事必须能被评测层证伪

| 叙事 | 暂停前事实 | 工程动作 |
|------|------------|----------|
| 「AI Native / 共创生成」像身份 | 实质多为预训练生成 + 微信读书 enrichment | 功能/体验评测应能打到「资料活水」；打不到就要降级叙事 |
| 「补 Agent / 检索就重生」 | 最多换更强工人，不自动产生护城河 | 定稿合同的 Goal 不能偷换成「接上某某 Agent」 |

**口令：宣传语进 Acceptance；验不过就改叙事或停，而不是加功能遮羞。**

### 2.2 自动化不能替代「值不值得做」

08-05 已写：自动化的是「已批准目标 → 可验证交付」，不是自动决定产品方向。  
暂停把这句话做实了：**流水线越顺，越容易在伪需求上加速**——所以要有显式停机条件，不只是 `Stop: 别无限 polish`。

### 2.3 失败要升格，不要永远挂在「体验反馈」

资料偏官方长期像 UX 问题；根因是未检索 / 能力边界。  
工程习惯：同一失败桶反复出现且修 UI 无效 → **升格为能力或身份问题**，进入诚实记账，而不是第 N 次 Persona 建议。

### 2.4 封板是工程制品，不是心情

暂停决议回答「为什么停」；封板交接回答「停在哪」：

| 制品 | 作用 |
|------|------|
| 冻结 tag（如 `freeze-2026-08-12`）+ 发行版 tag | 代码真源 |
| 功能清单 / 已实现回写勘误 | 能力真源 |
| 开放项冻结表 | 不定案、不否决、不排期 |
| 重启门槛（书面四问） | 防止默认「接着堆」 |

远端 `main`、tag、文档必须对齐；只停本地会话不算封板。

## 3. 与三层评测的关系

| 层 | 暂停暴露的缺口 |
|----|----------------|
| 代码 | 可继续干净；不是停机主因 |
| 功能 | 主路径可走通仍可「功能过、身份不过」 |
| 产品 | 「愿用」若建立在虚假能力预期上，体验优化是负债 |

因此：**产品层评测必须包含「用户以为系统能做什么」vs「系统真正承诺什么」**，否则 Persona 会优化错误目标。

---

## 4. 重启时的工程检查单（摘自产品 §5，工程视角）

书面答清之前，不恢复功能排期、不开增量流水线全自动：

1. 一句话身份是否改为「可视化 PDCA / 刻意练习外壳」？  
2. AI 层（薄 LLM / Agent / 外置）是否**不绑死身份**？  
3. 相对通用 Agent，不可替代步骤是什么？  
4. 资料关若要做：检索/Agent 是补丁还是主叙事？  

工程侧附加：

- [ ] 从冻结 tag 开分支，不从模糊「最新感觉」  
- [ ] 新定稿合同的 Acceptance 能证伪新叙事  
- [ ] 先恢复三层评测门禁，再谈 A2A / 大而全自动化  

---

## 5. 口令

**验不穿的卖点，不要写成身份。**  
**流水线越快，越需要停机闸门。**  
**封板 = tag + 能力真源 + 重启门槛，缺一不可。**
